## 1. Introducción

Se evaluaron tres alternativas de stack tecnológico mediante criterios multidimensionales alineados a:

- Restricciones del proyecto (presupuesto S/ 500,000, tecnologías de código abierto prioritarias).
- Perfil del equipo universitario (conocimientos intermedios en Python, desarrollo web y algoritmos).
- Requisitos de rendimiento (≤ 45 s para 150 pedidos / 15 vehículos).
- Criterios de sostenibilidad y bajo consumo energético en la nube.
- Escalabilidad futura (hasta 1,000 pedidos / 50 vehículos).

## 3. Justificación Técnica Formal de la Selección

**Stack seleccionado: Python / FastAPI + React + PostgreSQL + Leaflet/OpenStreetMap**

### 3.1 Razones principales

1. **Metaheurísticas y cómputo científico**  
   Python dispone del ecosistema más maduro y productivo para implementar Algoritmos Genéticos, Búsqueda Tabú y Optimización por Colonia de Hormigas (DEAP, OR-Tools, NumPy, SciPy). Esto es crítico para cumplir RNF-001 (≤ 45 s).

2. **Rendimiento y consumo de recursos**  
   FastAPI es asíncrono, de bajo consumo de memoria y genera documentación OpenAPI automáticamente. Ideal para un presupuesto limitado y criterios de eco-diseño.

3. **Alineación con el equipo**  
   El equipo ya posee conocimientos intermedios de Python y desarrollo web. La curva de aprendizaje es manejable dentro de las 14 semanas.

4. **Base de datos relacional**  
   PostgreSQL ofrece integridad referencial, soporte geoespacial (PostGIS) y excelente rendimiento para consultas de rutas y reportes. Cumple con la necesidad de datos estructurados (flota, pedidos, conductores, ventanas de tiempo).

5. **Frontend y mapas**  
   React + Leaflet/OpenStreetMap permiten una SPA moderna, responsive y de bajo consumo de datos (importante para RNF-009 – conectividad 2G/3G). Evita costos de Google Maps API en el MVP.

6. **Restricciones del proyecto**  
   Cumple estrictamente con C-03 (tecnologías prioritarias de código abierto) y con el presupuesto fijo de S/ 500,000.

## 4. Eco-diseño del Stack (Green Software)

La consigna exige aplicar los principios de **Green Software**. El stack seleccionado contribuye a reducir la huella de carbono del propio sistema —no solo la de la flota— mediante las siguientes decisiones:

| Decisión de eco-diseño | Implementación concreta | Efecto esperado |
|---|---|---|
| Backend asíncrono de bajo consumo | FastAPI + Uvicorn (I/O no bloqueante) | Menor número de instancias para la misma carga |
| Optimización de consultas | Índices estratégicos y consultas geoespaciales GiST (documento 11) | Menos CPU y menos tiempo de cómputo por petición |
| Transferencia mínima de datos | Respuestas JSON compactas, paginación, tiles de OpenStreetMap cacheados | Cumple RNF-009 (≤ 150 KB por sesión en Modo Conductor) |
| Cómputo bajo demanda | El Motor de Optimización solo se ejecuta cuando el Operador lo solicita o ante un evento de re-optimización | Evita procesamiento permanente en segundo plano |
| Infraestructura de bajo costo energético | Contenedores Docker en proveedores con planes de bajo consumo y, preferentemente, energía renovable | Reduce el consumo eléctrico asociado al servicio |

Esta sección es la referencia citada como *«Documento 10 (Eco-Design)»* en la restricción **RES-A4** del documento 13.
